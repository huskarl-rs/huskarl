# Validating RFC 9068 access tokens

[`Rfc9068Validator`](crate::validator::rfc9068::Rfc9068Validator) verifies
self-contained RFC 9068 JWT access tokens against the authorization server's
published signing keys. If your authorization server does not issue
RFC 9068-compliant tokens, follow the [custom validator
guide](crate::_docs::guide::custom) instead — see [choosing a
validator](crate::_docs::explanation::choosing_a_validator).

## 1. Set up your HTTP client

Use an HTTP client to fetch discovery metadata and signing keys:

```rust
use huskarl_reqwest::ReqwestClient;

# async fn setup_client() -> Result<(), Box<dyn std::error::Error>> {
let client: ReqwestClient = ReqwestClient::builder().build().await?;
# Ok(())
# }
```

## 2a. Build the validator from authorization server metadata

```rust
use huskarl_resource_server::{
    core::server_metadata::AuthorizationServerMetadata,
    validator::rfc9068::Rfc9068Validator,
};
# async fn example() -> Result<(), Box<dyn std::error::Error>> {
# let http_client = huskarl_reqwest::ReqwestClient::builder().build().await?;

let metadata = AuthorizationServerMetadata::fetch()
    .http_client(&http_client)
    .issuer("https://my-issuer")
    .call()
    .await?;

let validator = Rfc9068Validator::builder_from_metadata(&metadata)
    .audience("api://my-resource")
    .jwks_source(http_client.clone())
    .build()
    .await?;
# Ok(())
# }
```

## 2b. Alternative: Build without authorization server metadata

```rust
use huskarl_resource_server::validator::rfc9068::Rfc9068Validator;
# async fn example() -> Result<(), Box<dyn std::error::Error>> {
# let http_client = huskarl_reqwest::ReqwestClient::builder().build().await?;

let validator = Rfc9068Validator::builder()
    .issuer("https://my-issuer")
    .audience("api://my-resource")
    .jwks_uri("https://my-issuer/.well-known/jwks.json".parse()?)
    .jwks_source(http_client.clone())
    .build()
    .await?;
# Ok(())
# }
```

## 2c. Construction and defaults

`builder_from_metadata` copies the issuer and JWKS URI into the builder; it
performs no HTTP requests. `.audience(...)` supplies the audience your API
expects, and `.jwks_source(...)` selects verification using those published keys.

With this configuration, `.build().await` fetches the initial JWKS. A missing
URI or a failed fetch fails construction. Build the validator once and reuse
it across requests. Verification uses cached keys; key refresh can perform HTTP
requests during validation.

The default source refreshes keys on use after one hour and retries key misses
with refresh/backoff. Bearer tokens are accepted unless `.require_dpop(true)`
is set. Token and DPoP proof JTI replay checkers are optional.

## 2d. Customize the key source

Pass a configured [`JwksSource`](crate::core::jwk::JwksSource) to change refresh
or startup behavior. Choose `.jws_verifier_factory(...)` instead of
`.jwks_source(...)`; both configure the same builder field.

```rust
use std::time::Duration;

use huskarl_resource_server::{
    core::{
        jwk::{JwksSource, JwksStartup},
        server_metadata::AuthorizationServerMetadata,
    },
    validator::rfc9068::Rfc9068Validator,
};
# async fn example(metadata: &AuthorizationServerMetadata) -> Result<(), Box<dyn std::error::Error>> {
# let http_client = huskarl_reqwest::ReqwestClient::builder().build().await?;
let validator = Rfc9068Validator::builder_from_metadata(metadata)
    .audience("api://my-resource")
    .jws_verifier_factory(
        JwksSource::builder()
            .http_client(http_client)
            .ttl(Duration::from_secs(5 * 60))
            .startup(JwksStartup::FailFast)
            .build(),
    )
    .build()
    .await?;
# Ok(())
# }
```

Constructing `JwksSource` itself does no HTTP work. Its startup policy applies
when the validator builds the verifier. `FailFast` is the default;
`SeedEmpty` tolerates a failed initial fetch and retries during validation.
Requests needing unavailable keys fail until a refresh succeeds.

A custom factory can use its own keys without a JWKS URI. Factory and checker
setters accept concrete implementations or shared implementations in `Arc`.
With `default-jws-verifier-platform` disabled, supply
`.jws_verifier_platform(...)` explicitly.

## 2e. Choose replay checks

Use `.dpop_jti_checker(checker)` to reject reused DPoP proofs while allowing
an access token to be presented with a fresh proof on each request.
`.token_jti_checker(checker)` rejects reuse of the access token itself while
its JTI remains recorded; enable it only when that restriction is intended.

If both checkers use the same store, give them separate key namespaces and
retention periods covering their respective acceptance windows. The
`maybe_*` setters take optional shared checkers, including `None`.

## 3. Validate a request

Call
[`Rfc9068Validator::validate_request`](crate::validator::rfc9068::Rfc9068Validator::validate_request)
with the HTTP request headers, method, and URI. The
[`outcome`](crate::validator::ValidationResult::outcome) field of the result is:

- `Ok(None)` — no authentication header was present
- `Ok(Some(_))` — a valid token was found; the request is authenticated
- `Err(_)` — a token was present but invalid

The URI must be the **absolute external target URI** the client addressed
(scheme + authority + path): it is compared against the `htu` claim of any
DPoP proof (RFC 9449 §4.3). Framework request objects usually carry only the
origin-form path (`/resource`), and behind TLS-terminating or rewriting
proxies only your deployment knows the external URI — reconstruct it from a
configured public base URL or from forwarded headers you trust. A
non-absolute URI fails every DPoP validation with an integration error.

```rust
# use huskarl_resource_server::core::server_metadata::AuthorizationServerMetadata;
# use huskarl_resource_server::validator::rfc9068::Rfc9068Validator;
# async fn example() -> Result<(), Box<dyn std::error::Error>> {
# let http_client = huskarl_reqwest::ReqwestClient::builder().build().await?;
# let metadata = AuthorizationServerMetadata::fetch()
#     .http_client(&http_client)
#     .issuer("https://my-issuer")
#     .call()
#     .await?;
# let validator = Rfc9068Validator::builder_from_metadata(&metadata)
#     .audience("api://my-resource")
#     .jwks_source(http_client.clone())
#     .build()
#     .await?;
use http::{HeaderValue, Method, Uri, header::AUTHORIZATION};

let mut headers = http::HeaderMap::new();
headers.insert(AUTHORIZATION, HeaderValue::from_static("Bearer mF_9.B5f-4.1JqM"));
let method = Method::GET;
let uri = Uri::from_static("https://api.example.com/resource");

let result = validator.validate_request(&headers, &method, &uri, None).await;

match result.outcome {
    Ok(Some(validated)) => println!(
        "Authenticated: subject={:?}, scope={:?}",
        validated.sub,
        validated.claims.scope,
    ),
    Ok(None) => println!("No authentication provided"),
    Err(e) => println!("Validation failed: {e}"),
}
# Ok(())
# }
```

## 4. Reject a request

A rejection response has up to three ingredients: the status code, one or
more `WWW-Authenticate` challenges, and — for DPoP — a `DPoP-Nonce` header.
[`ValidationResult::rejection`](crate::validator::ValidationResult::rejection)
assembles all three from the validator's
[metadata](crate::validator::metadata::ProvideValidatorMetadata::validator_metadata);
[`Rejection::apply`](crate::rejection::Rejection::apply) stamps them onto an
`http` response builder (or read the [`Rejection`](crate::rejection::Rejection)
fields and use your framework's own response type).

```rust
# use huskarl_resource_server::core::server_metadata::AuthorizationServerMetadata;
# use huskarl_resource_server::validator::rfc9068::Rfc9068Validator;
# async fn example() -> Result<(), Box<dyn std::error::Error>> {
# let http_client = huskarl_reqwest::ReqwestClient::builder().build().await?;
# let metadata = AuthorizationServerMetadata::fetch()
#     .http_client(&http_client)
#     .issuer("https://my-issuer")
#     .call()
#     .await?;
# let validator = Rfc9068Validator::builder_from_metadata(&metadata)
#     .audience("api://my-resource")
#     .jwks_source(http_client.clone())
#     .build()
#     .await?;
# let headers = http::HeaderMap::new();
# let method = http::Method::GET;
# let uri = http::Uri::from_static("https://api.example.com/resource");
let result = validator.validate_request(&headers, &method, &uri, None).await;

let validator_metadata = validator.validator_metadata(Some("https://api.example.com"));
if let Some(rejection) = result.rejection(&validator_metadata, Some("read")) {
    // 401/403/5xx with the right WWW-Authenticate challenges and DPoP-Nonce.
    let response = rejection.apply(http::Response::builder()).body(String::new())?;
    # let _ = response;
    return Ok(()); // …send `response`…
}

// Authenticated. A nonce can arrive on success too (rotation): echo it.
let mut response = http::Response::builder().status(http::StatusCode::OK);
if let Some(nonce) = &result.dpop_nonce {
    response = response.header("DPoP-Nonce", nonce.as_str());
}
# let _ = response;
# Ok(())
# }
```

Two decisions stay with your application:

- **Anonymous endpoints.** `rejection` treats "no credentials" as a 401 with
  the unauthenticated challenges. If the endpoint also serves anonymous
  requests, match on [`outcome`](crate::validator::ValidationResult::outcome)
  instead and only reject `Err(_)`.
- **Authorization.** A valid token may still not authorize the request. For
  a scope failure, build the 403 from the metadata directly:
  [`ValidatorMetadata::rejection`](crate::validator::metadata::ValidatorMetadata::rejection)
  with [`InsufficientScope::new("required scope")`](crate::error::InsufficientScope)
  — the error carries the scope the challenge advertises — or
  [`InsufficientUserAuthentication`](crate::error::InsufficientUserAuthentication)
  for RFC 9470 step-up.
